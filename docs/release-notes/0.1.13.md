**CodeWitness 0.1.13** moves the project's account of its own releases into the repository.

## What changed

- **Release notes live in `docs/release-notes/<version>.md`.** They used to sit beside the checkout, outside
  version control, which meant the repository could not say what its own releases contained: a clone had the
  code for 0.1.11 and no record of why 0.1.11 existed. The notes for **0.1.5 through 0.1.12** are backfilled, and
  the notes for this release are the first that were written in the repository in the first place.
- **A release is a tag, and `README.md` now says what that means**: the tag, the root `pom.xml` version (which
  every module inherits) and the version the tool reports must agree, or the release is wrong in a way nobody
  can debug later. Every release so far has been cut with those three checks by hand.
- **The workflow that enforces them is written but not yet in the repository.** `.github/workflows/release.yml`
  builds the shaded jar on a `v*` tag, refuses to publish unless those three versions agree, checks that the jar
  runs and reports the version being released, and attaches it to a GitHub release whose notes come from
  `docs/release-notes/<version>.md`. It could not be pushed with the token this session runs under, which may
  not create workflow files; it is staged for the next change, and the release it describes was cut by hand as
  every previous one was.

## Verified for this release

- Full reactor test suite: **1725 tests, 0 failures** across all 22 modules.
- The three version numbers were checked against each other before the tag was cut, and
  `java -jar codewitness-cli/target/codewitness.jar version` reports `0.1.13` from the jar attached to the
  release.

## Compatibility

- No change to the tool: no report format, verdict, exit code, CLI or configuration behaviour differs.

**CodeWitness 1.0.9** points the tool's strongest technique at its own verdict logic, and the first run found a real
gap in it.

## What changed

- **Mutation testing runs over the verdict logic in the self-check.** `selfcheck/codewitness.yaml` scopes PIT to
  `VerdictCalculator` and `BudgetUsage` — the code that decides every requirement's verdict — rather than the whole
  reactor, which would take longer than the rest of the run for a number about test strength in general. The suite
  now kills **31 of 31 mutants (100%)**.
- **The first measurement was 96.8%, and the survivor was worth having.** It was a negated conditional at
  `VerdictCalculator:81`, in the branch added in 1.0.5 so that a counterexample observed alongside a failed build is
  named in the verdict instead of discarded. The surviving mutant emitted *"An executed experiment did record 0
  counterexample(s)"* when there were none: a fabricated observation, inside the one report whose value is that it
  only says what it saw. The suite covered the has-a-counterexample case and not the has-none case — the direction
  that matters more. A test pins it now.
- **`mutation.target_classes` was documented and inert.** The Java adapter derived PIT's target from the project's
  `rootPackages` attribute and never read the configuration, so a run asking to mutate two classes mutated the whole
  reactor: 2,538 mutants and a 73.5% score that said nothing about the verdict logic. The adapter reads the configured
  list first now, falling back to the project's roots. The defect was found by pointing the tool at itself with a
  scoped target and reading the count it reported.
- **The project declares PIT in its own `pom.xml`.** The adapter deliberately does not modify the project under
  verification, and PIT refuses to run against JUnit 5 tests without the `pitest-junit5-plugin` dependency. The
  adapter says exactly that, with the XML to add, rather than guessing — so the fix is a change to this project's build
  file, not a special case in the adapter. The plugin is never bound to a lifecycle phase; it runs only when a goal is
  asked for.

## Verified for this release

- Full reactor test suite: **1747 tests, 0 failures** across all 22 modules (up from 1746).
- The self-check reports all seven requirements `VERIFIED` with mutation testing measured: 31 mutants, 31 killed, 0
  survived, 0 with no coverage.
- The scoped run takes about two minutes; the unscoped one took seven and measured nothing useful about the verdict
  logic.

## Compatibility

- New behaviour: `mutation.target_classes` is honoured (it previously had no effect). A project that set it and saw
  the whole reactor mutated will now see only what it named.
- No report format, verdict, exit code, CLI or configuration-schema change.

**CodeWitness 0.1.7** is an operations release. It makes a history survive the places histories are kept —
read-only mounts, shared caches, container images — and gives that history a size it can be held to.

## What changed

### Run retention

- **`report.keep_runs: N`** prunes all but the N most recent runs after a successful `verify`, deleting each
  run's index rows with its directory. Every run copies the project into its workspace, so a history grows
  with the tree: three runs of this repository are 97 MB, and nothing pruned them automatically.
- Retention is **off by default**. Deleting a history nobody asked to delete is not a safe default, and a
  project that wants the guarantee can set the number.
- It runs after the reports are written and the run is stored, so it can never delete the run that just
  finished.

### Reading a history where writing is impossible

- `report`, `reproduce` and the run listing now open the index **read-only**: no schema creation, no
  migration, no pragmas, and no database file created where none exists. A read is a different operation
  from a write and no longer requires write access to the directory for its own sake.
- A storage restriction — a read-only mount, a directory the process may not write, a database another run
  holds — is now a **statement about the history** with exit `3`, not an internal failure. Previously it
  produced a stack trace and filed a CRITICAL self-issue against CodeWitness, which was wrong about the cause
  and made the history unreadable exactly where a history is most useful.
- The distinction is made where the failure is understood: `StorageUnavailableException` marks a history that
  cannot be reached from here (read-only, locked, unopenable), while a **corrupt** database remains a defect
  that is journalled. Classification walks the cause chain, so it does not depend on which layer threw last.
- Where the index genuinely cannot be read, `report <run-id>` still works: it reads the stored report files
  directly and needs no database. The message says so.
- A read-only open of a database whose write-ahead log was never checkpointed says exactly that, and what to
  do about it, instead of surfacing a driver error.

## Verified for this release

- Full reactor test suite: **1703 tests, 0 failures** across all 22 modules (up from 1700); the new tests
  cover retention configuration, a read-only store refusing writes while still reading, a read-only store
  never creating a file, and the existing contract that a *corrupt* index is still journalled as a defect.
- End-to-end against the built jar: four verifies with `report.keep_runs: 2` left exactly two run
  directories; with `.codewitness` made read-only, `report` printed a single actionable line naming the
  restriction and the workaround with exit 3 and filed **no** self-issue, while `report <run-id>` printed the
  stored report normally.

## Compatibility

- New key: `report.keep_runs` (default `0`, meaning keep everything).
- A read-only history can now be listed where the database is not in WAL mode with pending writes; where it
  cannot, the message explains why instead of failing with a stack trace.
- No report format, verdict or exit-code change beyond the storage classification above.

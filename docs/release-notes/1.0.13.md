**CodeWitness 1.0.13** points the tool at itself and acts on what came back. Fourteen findings: nine were the rules'
own precision, now fixed; five are judgements the project states instead of hiding.

## What changed

- **`CW-CONC-001` no longer fires on builder classes.** A builder is created, filled and read by the thread that wants
  the object; sharing one is a bug in the caller. Eight of the fourteen findings were builders — the evidence chain's
  `Evidence.Builder`, `ProcessSpec.Builder`, `BuildResult`, `ProjectInfo`, `VerificationReport`, `AdapterProviders`
  and `VerificationContext`. A rule that flags every builder in a codebase is a rule that teaches its readers to skim.
- **Both rules now read code, not text.** `CW-CONC-001` flagged `private ulong _state;` inside the C# scenario
  generator's string literal, and `CW-SEC-004` flagged `new ProcessBuilder(...)` inside the Java generator's — both
  templates for code that is *emitted*, not code that is *here*. The concurrency scan now runs on the literal-blanked
  view the analyzer already builds for other checks, and `Rule` gained a `codeOnly` flag so the process-execution rule
  can too. The SQL rules deliberately keep reading literals: their evidence *is* the literal.
- **A fair finding about this author's own test.** `CW-TEST-001` reported a test with no assertion, and it was right:
  the test ended with a call to a helper that throws. It now asserts explicitly. A rule that only recognises JUnit's
  assertion methods would be a rule about spelling; this one is about whether a test can fail, and it caught a test
  whose only failure path was a helper's `AssertionError`.
- **Five findings survive and are suppressed with reasons**, in `selfcheck/codewitness.yaml`: two `CW-CONC-001` on
  `RunState`/`BudgetUsage` (the engine is strictly sequential — making them atomic would advertise a concurrency the
  design does not have), `CW-SEC-004` on `LocalProcessSandbox` (executing a command is what it is for, and the command
  comes from CodeWitness, not from the project), and two `CW-SEC-002` on `PRAGMA` statements (a PRAGMA takes no bind
  parameters and both interpolate an `int`). Suppression is disclosed by the run, with rule and reason.
- The self-check therefore ends with **no unexplained findings** — which is the only state in which a findings list is
  worth reading.

## Verified for this release

- Full reactor test suite: **1754 tests, 0 failures** across all 22 modules (up from 1751).
- New tests pin both precision fixes from both sides: process execution inside a string literal is not reported,
  a builder's fields are not reported as races, and ordinary shared mutable state still is — so the exclusion is
  narrow rather than a blanket silence.
- The self-run was repeated after each change: fourteen findings, then seven, then five, then zero with five disclosed
  suppressions, and the run still reports all seven ground rules `VERIFIED` with mutation at 100%.

## Compatibility

- New behaviour in the Java heuristic analyzer: fewer findings, because two rules no longer report text as code. A
  project that was seeing either false positive will see its finding disappear; nothing that was a true positive stops
  being one.
- No report format, verdict, exit code, CLI or configuration-schema change.

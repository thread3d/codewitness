**CodeWitness 1.0.2** adds process scenarios, and with them the last ground rule this tool could not prove about
itself. For the first time, every requirement in its own self-check is `VERIFIED` by execution.

## What changed

- **`mode: process`** — a scenario may now run a command and assert on what it returned: `exit_code`,
  `stdout_contains`, `stderr_contains`. Every other mode calls code *inside* the project's test framework, which
  cannot observe what a caller of the built program sees. An exit-code contract is a property of a process, so
  before this mode nothing could express one.
- **It closes a real gap in CodeWitness's own verification.** `CWR-007` — "CLI exit codes are part of the
  interface" — was the one requirement its self-check reported `UNVERIFIED`, because a generated test cannot
  observe an exit code. `selfcheck/codewitness.yaml` now runs the built jar and asserts exit `3` on a usage error;
  the self-check reports **all seven requirements `VERIFIED`, overall `VERIFIED`, exit `0`**.
- **`command` is argv, not a shell string.** No shell means no quoting rules to get wrong and no place for a value
  to become a second command. `${project_root}` is substituted with the original project tree, because the isolated
  copy excludes build output by design — a jar this run just built is not in the copy. Using it is recorded in the
  run's limitations, since the command then reads the real tree.
- **`expect` is declarative, not an expression language.** A process has three observable outcomes, and an
  expression evaluated inside CodeWitness would be a second scenario language whose semantics differ from the
  invariant every other mode evaluates in the project's own environment.
- **A command that cannot start is `UNVERIFIED`, never a failure.** A missing binary says nothing about the code
  under verification — the same reasoning that makes a failed build `BLOCKED` rather than `FAILED`.
- Error messages printed directly by commands now carry the `codewitness:` prefix that every other diagnostic uses;
  three of them (`verify`, and two in `init`) did not.

## Verified for this release

- Full reactor test suite: **1734 tests, 0 failures** across all 22 modules (up from 1729). The new tests run real
  processes: a command that behaves as declared discharges its obligation with deterministic evidence; a wrong exit
  code produces a counterexample carrying the argv and both codes; stdout text does not satisfy a stderr assertion;
  a command that cannot start is unverified, not failed; and a requirement with no process scenario says so.
- **The self-check itself**: `./codewitness verify . --requirements selfcheck/requirements.yaml --config
  selfcheck/codewitness.yaml` reports seven of seven `VERIFIED`, overall `VERIFIED`, exit `0`.
- Three defects were found by that self-check rather than by the unit tests, and are worth recording because each
  was a plausible-looking mistake: evidence was minted but never added to the ledger, so the experiment was
  invisible to the verdict and the requirement came out `PARTIALLY_VERIFIED` with "0 of 1 obligations remain
  unverified"; the evidence also carried no requirement, so it could not have been found even if it had been
  recorded; and a process that never started was initially reported as a violated expectation, turning a missing
  binary into a defect in the code.

## Compatibility

- Additive: a new scenario mode, two new scenario keys, one new obligation kind and evidence type. Every existing
  scenario, report key and exit code is unchanged. A `codewitness.yaml` written for 1.0.1 parses and behaves
  identically.

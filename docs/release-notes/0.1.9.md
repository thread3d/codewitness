**CodeWitness 0.1.9** replaces the fourteen copies of the boundary-case enumeration with one, and records the
truncation rule it enforces — including the limitation that rule has.

## What changed

- **One boundary-case enumeration.** `ScenarioCases.boundaryCases` in `codewitness-adapter-support` is now the
  only implementation; the fourteen private copies (one per adapter plus the one inside the shared module
  itself) delegate to it. The enumeration decides *which experiments run*, so fourteen answers to it were
  fourteen possible verification results for the same scenario.
- **The copies had drifted into three different truncation strategies.** One capped only at the end (an
  unbounded intermediate list for a pathological scenario); two capped at every stage. Both now follow one
  rule with the working set bounded while it grows — eight inputs of ten values each is a hundred million
  combinations, of which twelve are kept, and the intermediate list is bounded too.
- **The truncation rule is now written down instead of assumed.** Keeping the head of a breadth-first
  expansion holds the earliest-declared inputs at their first value and varies the later ones: with four
  inputs of six values, the kept twelve cases never move the first two. Every case is complete and valid, so
  nothing is mis-generated, but a scenario that expects all of its inputs exercised does not get that once the
  product exceeds the cap. Sampling the product so that every input varies (one-at-a-time variation plus
  pairwise combinations — the usual reading of "boundary values") changes which experiments run, so it belongs
  in its own release with the fixtures re-baselined. It is in the backlog for that reason, not forgotten.

## Verified for this release

- Full reactor test suite: **1713 tests, 0 failures** across all 22 modules (up from 1707). The new tests pin
  the shared behaviour: no inputs or an input with no declared values produces no cases, a single input yields
  one case per value, every generated case names every input, the pathological case stays bounded, case order
  is stable, and the truncation rule behaves as documented.
- All existing adapter tests for the four adapters whose code changed (C++, Pascal, Swift, and the shared Node
  generator) pass unchanged, which is the evidence that unifying the strategy did not alter the cases they
  cover.

## Compatibility

- Maintainability release: no report format, verdict, exit code, CLI or configuration change. A scenario whose
  product is under the cap generates exactly the cases it generated before.

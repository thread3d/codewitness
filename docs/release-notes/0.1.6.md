**CodeWitness 0.1.6** makes findings usable where reviews happen. A finding that cannot reach the code it
is about is a line in a report nobody opens, so this release adds the three things that turn advisory
findings into review comments: SARIF for code scanning, a baseline so a pull request shows only what it
introduced, and suppression so a known false positive can be named instead of ignored.

CodeWitness does not generate code. It compiles the project, runs its tests, analyses it,
generates additional adversarial tests, executes them, looks for counterexamples, and reports
what it actually observed — with the evidence attached. A language model's opinion is recorded
as a suggestion and never counted as proof.

## What changed

### SARIF 2.1.0 export

- `verify --sarif <file>` writes a SARIF report, and `report.sarif: true` writes `report.sarif` beside the
  other run artifacts. This is the format GitHub code scanning, GitLab's SAST report and an editor's
  Problems panel already understand, so a finding arrives where the code is.
- One **rule** per rule id that fired, one **result** per finding, and the finding's fingerprint as a
  `partialFingerprints.codeWitnessFingerprint`, so a code host can tell a recurring finding from a new one.
- **Counterexamples are results too**, always at level `error`. A counterexample is the one output of this
  tool that is proof rather than advice, and dropping it from the machine-readable output would repeat the
  mistake that 0.1.5 fixed in the HTML report.
- The invocation's `executionSuccessful` reflects the **run status**, not the verdicts: a run that found
  counterexamples still executed, and a `BLOCKED` run did not finish. A truncated scan cannot be uploaded as
  a clean one. The run's limitations travel in `toolExecutionNotifications`.
- Severity maps onto SARIF's three levels (`CRITICAL`/`HIGH` → `error`, `MEDIUM` → `warning`, the rest →
  `note`) and each result keeps the original in `properties.codeWitnessSeverity`, because a heuristic HIGH
  and a compiler HIGH are not the same claim.

### Baselines

- `verify --baseline <report.json>` (or `findings.baseline`) reports only the findings a previous run did
  not contain — the question a pull request actually asks.
- Identity is the finding fingerprint (analyzer, rule, file, line, message), so a finding that moved is
  reported again: re-reporting a moved finding is noise, hiding a new one is a miss.
- The number of findings the baseline accounted for is stated in the run's limitations, since a baseline
  that hides a growing backlog without saying so would be exactly the dishonesty this tool exists to avoid.
- A baseline that cannot be read reports everything and says why; it never silently degrades to "no
  baseline".
- `report.json` findings now carry a `fingerprint`, which is what makes a report usable as the next run's
  baseline.

### Suppression

- `findings.suppress` names a rule, an optional path and a reason:

  ```yaml
  findings:
    suppress:
      - rule: CW-CONC-001
        reason: immutable model classes built through a builder
  ```

- An entry without a rule id is rejected: it would either suppress nothing or suppress everything. Unknown
  keys inside an entry are rejected like every other configuration mistake.
- The run states how many findings were suppressed, by which rules and for what reason, in its
  limitations. The rules stay installed — suppression is a claim about these findings in this project, not a
  finding that the rule is wrong.

### Configuration and interface

- New keys: `report.sarif`, `findings.baseline`, `findings.suppress[].{rule,path,reason}`.
- New flags: `verify --sarif <file>`, `verify --baseline <report.json>`.
- The configuration fingerprint now covers the suppression list, because suppressions change what a run
  reports.

## Verified for this release

- Full reactor test suite: **1700 tests, 0 failures** across all 22 modules (up from 1684); the new tests
  cover the SARIF document (header, rules, levels, locations, counterexample level, blocked-run invocation,
  writing to disk), baseline loading (fingerprint identity, not-a-report, malformed JSON, missing file) and
  suppression parsing (rule/path/reason, rule-less entry, unknown key).
- End-to-end against the built jar: a Python project with a concatenated SQL statement produces one SARIF
  result (`CW-PY-SEC-008`, level `error`) with a project-relative location and line 2; a second run with
  `--baseline <first report.json>` produces **no** results and states the baseline in its limitations; the
  same project with `findings.suppress` naming that rule produces no results and a limitation naming the
  rule and the reason.
- One defect was found and fixed while wiring suppression: both the CLI and the MCP server rebuilt the
  configuration through a 13-argument constructor that dropped the new `findings` section, which made every
  suppression silently do nothing. Both sites now carry it, which is the sort of mistake the compatibility
  overload invites and the reason it is documented as meaning "no suppressions".

## Compatibility

- `report.json` findings gain a `fingerprint` key; no key was removed or retyped.
- `report.sarif` is written only when asked for, so existing pipelines are unaffected.
- A baseline pointing at a report written by 0.1.5 or earlier reports every finding, because those reports
  have no fingerprints; the limitations say the baseline accounts for zero findings.

**CodeWitness 1.0.16** closes the second defect the self-check reported about itself: a limitation said a
requirement could not be exercised, in the same report that recorded it being exercised.

## What changed

- **The generated-tests phase no longer denies a scenario that exists.** When a requirement declares a
  scenario the generator cannot render as a test, the strategy used to announce *"No executable scenario
  is declared for CWR-007, so CodeWitness could not run any experiment against it. Declare a scenario in
  codewitness.yaml to make this requirement verifiable."* For this project's own exit-code requirement
  that sentence was false twice over: `SC-CWR-007` is declared, and the process phase ran it, asserted
  exit code `3` and discharged the obligation to `VERIFIED` (evidence `EV-021`). The report's
  "things CodeWitness could NOT verify" section therefore listed a requirement the run had just verified
  by executing something.
- **The two cases are now distinguished, and both statements are true.** With no scenario at all, the
  phase says so and suggests declaring one. With a scenario that exists but cannot become a generated
  test — a process scenario, which the process phase runs unless it asks for a native test — it says
  *that*, and points at the requirement's own evidence for what did run.
- **The obligation outcome recorded in the same branch had the same fault.** It read *"No declared
  scenario produces an executable experiment for this obligation"*, which is false for the same reason.
  It now says the generated-test strategy produced no experiment because the declared scenario cannot be
  expressed as one. A stronger outcome from the process phase used to hide this at the merge; that is
  luck, and the reason is now true on its own.
- **The process phase made the mirror-image claim.** A **process** scenario that asks for a native test
  is deliberately not run by the process phase (the generated test runs it, so the assertion is not
  executed twice). When every process scenario for a requirement was of that kind, the phase reported
  *"No process scenario was declared for R-001"* — again denying a scenario the project had declared.
  It now says the declared scenario asks for a native test and that whether the command ran at all
  depends on the generated-test phase, which writes the test or reports why it could not.

Both defects are the same mistake in opposite directions: a note written from what the *strategy* could
see ("I have nothing to run") was phrased as a fact about the *configuration* ("there is nothing
declared"). The report is not allowed to make the second claim from the first.

## What this does not fix

- The self-check's evidence for the exit-code requirement is still `INCONCLUSIVE` from the *existing
  tests* strategy, because its declared `@Tag("e2e")` class never runs in the default suite. That is the
  correct record — the obligation is verified by the process scenario, not by that class — and 1.0.15
  made it honest rather than silently supportive.
- Nothing here changes a verdict. Both messages were unknown aspects, which by design cannot affect a
  verdict or an exit code; they were wrong about what the run had done, not about what it concluded.

## Verified for this release

- Full reactor suite: **1759 tests, 0 failures** across all 22 modules (up from 1757: two regression
  tests for the generated-tests phase, plus the assertions added to the process-phase test that pins
  the native-test branch).
- **Both guards were proved to fire.** The generated-tests test fails against the old strategy with the
  note it produced (`No executable scenario is declared for R-001 …`), and the process-phase test fails
  with `No process scenario was declared for R-001 …` for a requirement that declares one. Both pass
  after the change.
- A companion test pins the *other* branch: with no scenario declared, the note that says so is still
  produced. A fix that silenced both cases would hide a real gap.
- Self-check (`./codewitness verify . --requirements selfcheck/requirements.yaml --config
  selfcheck/codewitness.yaml --no-mutation --max-duration 30m`): all seven ground rules `VERIFIED`, 0
  unsuppressed findings, exit `0`. The exit-code requirement's unknown aspects now read *"The
  generated-test strategy produced no test for CWR-007: its declared scenario(s) cannot be expressed as
  a generated test here, and a process scenario is run by the process strategy unless it asks for a
  native test. This requirement's own evidence records what did run."* — and its obligation remains
  `VERIFIED` by `SC-CWR-007`.

## Process note

Writing the regression test, I first quoted the requirement's id in a code comment. The mapping is by
mention — a test source that names a requirement is mapped to it — so the two test classes became
*evidence* for that requirement, and the self-check's evidence line went from "1 classes, 0 executed" to
"2 classes, 7 passing": seven strategy tests counted as support for a CLI exit-code contract they say
nothing about. The self-check's own output is what showed it. The comments now describe the requirement
without naming it, and the evidence is back to the honest "1 classes, 0 executed" this release is about.

## Compatibility

- No interface change: CLI, exit codes, report keys, SARIF and every `codewitness.yaml` key are
  untouched. Two sentences in the unknown-aspects list change, and one obligation outcome's rationale
  in a case that previously went unmerged. Verdicts are unchanged: these notes never reached one.

**CodeWitness 1.0.11** lets a process scenario become a test in the project's own suite, and fixes a defect in what
the generators were emitting for one.

## What changed

- **`native_test: true` on a process scenario generates a real test in the project's framework.** The Java adapter
  writes a JUnit 5 class that starts the command with `ProcessBuilder`, drains both streams, compares the exit code
  and the expectations, and prints the shared `CODEWITNESS_COUNTEREXAMPLE|…` line before failing; the Python adapter
  writes the equivalent `unittest` case with `subprocess.run`. So the assertion can live in the suite that will still
  be there when CodeWitness is not — which was the point of every other scenario mode, and was the one thing process
  mode could not do.
- **The engine steps back when the project asks for that.** A scenario marked `native_test` is executed by its
  generated test, not twice: `ProcessScenarioStrategy` skips it, because otherwise one violation would produce two
  counterexamples and one command would run twice.
- **A real defect is fixed on the way.** A `process` scenario that was *not* marked `native_test` reached the
  step-based renderer, which has no steps, observation or invariant to render — and emitted a Python test containing
  `try:` with an empty body. It was syntactically invalid, so the runner failed to import it, and the run reported a
  generated test that could not run while the real assertion was made by the engine. The generators now skip a process
  scenario they have nothing to render, explicitly rather than by accident.
- **`${project_root}` resolves when the test runs, not when it is written**, in both generated languages
  (`os.getcwd()`, `System.getProperty("user.dir")`). A generated test cannot know the absolute path of the checkout it
  will eventually live in, and baking one in would make it pass on the machine that generated it and nowhere else.

## Verified for this release

- Full reactor test suite: **1750 tests, 0 failures** across all 22 modules (up from 1747).
- **Both adapters were exercised end to end, not only inspected.** A real Maven JUnit 5 project and a real Python
  project each verified a process scenario with `native_test: true`: on success the requirement came out `VERIFIED`
  with the generated test as the executing experiment, and on a violation the run exited `1` with `CE-001` carrying the
  observed exit code and the assertion that failed — for Java through `mvn test` and for Python through the generated
  `unittest` module.
- New tests pin the generated source (a `subprocess`-based `unittest` case with the declared command, exit code and
  streams; `native_test` parsing on a process scenario and its rejection on any other mode) and, importantly, that a
  process scenario *without* `native_test` now generates nothing rather than a broken file.

## Compatibility

- Additive: one new scenario key, `native_test`, defaulting to `false`. A scenario that does not use it behaves
  exactly as before — except that a `process` scenario no longer produces an invalid generated test alongside the
  engine's own execution.

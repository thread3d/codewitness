**CodeWitness 1.0.22 brings the CI workflow's action pins to the releases their own comments name, and stops the
repository from being able to acquire a mutable tag pin — or two versions of one action — without the fast suite
failing.**

## What changed

- **Four pins were behind the release recorded beside them, and one of them was behind in three files at once.**
  Sixteen `uses:` lines across three workflow files pin twelve distinct actions to a commit SHA; a SHA never moves
  on its own, which is the point of it, so each was resolved deliberately from upstream's tag to its commit:

  | Action | Was | Now |
  | --- | --- | --- |
  | `actions/setup-java` | v6.1.0 | v6.2.0 |
  | `actions/setup-python` | v7.0.0 | v7.1.0 |
  | `actions/setup-dotnet` | v6.0.0 | v6.1.0 |
  | `ruby/setup-ruby` | v1.329.0 | v1.338.0 |

  `setup-java` is pinned in `ci.yml`, `codeql.yml` and `release.yml`. All three moved together, because a pipeline
  that builds on v6.1.0 in its CodeQL job and v6.2.0 in its test job is running two versions of one action, and the
  one nobody looked at is the one that did not get reviewed.

  Each tag was resolved to a commit with the GitHub API rather than copied from a report — the same API that a
  dependency scanner read when it offered `shivammathur/setup-php` an "update" to `verbose`, which is a tag on that
  repository and not a version of anything.

- **`CiActionPinsTest` now holds the invariant `ci.yml` stated only in prose.** The workflow's comment block claims
  every action is pinned to a full-length commit SHA rather than a movable tag; that claim had no test behind it,
  and `uses: actions/checkout@v4` is exactly the line a hurried "fix the CI" commit writes. The test checks three
  things across every workflow file:

  - every `uses:` names a 40-character commit SHA — no tag, no branch, no short SHA;
  - every SHA carries a `# <release>` comment, because `.github/dependabot.yml` reads that comment to know which
    release a SHA is, and a pin without one quietly stops being tracked;
  - the same action is pinned to one SHA across the whole pipeline.

- **The reactor-root walk-up was extracted rather than copied.** `PackagingNativeAccessTest` already walked up from
  the working directory to find the aggregator POM, because Surefire's working directory is the module directory
  and differs between a full reactor build and `./mvnw -pl codewitness-cli test`. The new test needs the same
  walk-up and the same subtle rule that distinguishes the reactor root from a module POM that merely names
  `codewitness-parent`, so it moved into `ReactorRoot` and both tests call it.

- **Left alone on purpose.** `dtolnay/rust-toolchain` is a commit at the tip of a moving `stable` branch with no
  release tag; `dependabot.yml` says it must be refreshed deliberately, and refreshing it here would move the Rust
  fixture's compiler as a side effect of a housekeeping release. The two `github/codeql-action` pins are also
  untouched: their tags are `codeql-bundle-v*` rather than semver, and reconciling them is a different question
  from adopting four minor bumps.

## What this does not fix

- **It does not keep the pins current; it keeps them well-formed.** The test asserts the *form* of a pin, not its
  currency. A pin can be a valid full-length SHA with a correct version comment and still be a year old, and
  noticing that needs the network — which is why it stays Dependabot's job. The mechanism is imperfect in a way
  worth recording: the one open Dependabot pull request covers two of these four actions, and by the time it was
  read its `ruby/setup-ruby` pin proposed v1.336.0 when v1.338.0 was current. A grouped PR is only as fresh as the
  day it opened.

- **It cannot tell whether a SHA belongs to the repository named beside it, or whether the comment is the release
  that SHA came from.** Both need upstream, and both are what a bad manual edit gets wrong. The test catches a
  missing comment and a disagreeing pair of pins; it would not have caught a comment reading `v6.2.0` beside
  v6.1.0's commit, which is why the four bumps here were resolved from the API rather than hand-typed.

- **`github/codeql-action` still gets no update proposal from anything.** A scanner that splits an action reference
  on its final `/` reads `github/codeql-action/init` as a repository named `codeql-action/init`, gets a 404, and
  drops both `init` and `analyze` from its results entirely. The new test covers those pins' *form* — they are
  well-formed and consistent — but nothing proposes their next release.

- **No behaviour changes.** No adapter, phase, verdict rule, report field, budget or exit code is touched. The one
  user-visible difference is the version string in reports.

## Process note

This release was found by pointing a dependency-scanner MCP server (`depmcp` 0.11.0) at the repository rather than
by a human noticing, and the way it went wrong is the useful part. The scanner has no Maven support, so of the
project's 23 POMs it read none: its 21 "dependencies" were the workflow pins, one `setuptools` constraint, and four
entries that are not dependencies at all — `requires-python` looked up on PyPI as a package, and the fixtures'
own `version = "0.1.0"` field matched against a 2014 PyPI package literally named `version`, which it then
proposed bumping to 0.1.1. That is why the pins here were resolved from the GitHub API by hand and no update plan
was applied: the plan contained two entries that would have broken the repository, and applying it applies every
group at once.

The near-miss is worth recording because the new test caught it: the first pass at this change bumped
`actions/setup-java` in `ci.yml` only. The version-comment and SHA assertions both passed, and the pipeline would
have run v6.2.0 for tests and v6.1.0 for CodeQL — a difference invisible in review, in a green build, and in the
report. The third assertion exists because of that mistake.

## Compatibility

- No CLI command, flag, exit code, report key, SARIF profile, configuration key or adapter-SPI change. A project
  verified by 1.0.21 is verified identically by 1.0.22; only `version` in the report differs.
- The two new test-visible files are `ReactorRoot` and `CiActionPinsTest`, both in `codewitness-cli`'s test tree;
  neither is part of any published artifact.

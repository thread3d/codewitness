**CodeWitness 1.0.15** closes the first of two defects the self-check reported about itself: a mapped test
class that ran no case at all was scored as evidence that supports the requirement.

## What changed

- **A mapped test class must contribute at least one executed case before the project's own suite can
  support anything.** `ExistingTestsStrategy` recorded `SUPPORTS` evidence — with confidence `HIGH` —
  and a `PARTIALLY_VERIFIED` outcome for every obligation, whenever the requirement's `tests:`
  declaration named a class. It never checked that the class contributed a case. When the suite runs
  and reports nothing for the mapped classes — excluded by a tag, filtered out, not discovered — the
  record now has status `INCONCLUSIVE`, every non-manual obligation is reported `UNVERIFIED` with a
  reason, and a note says the mapped class ran nothing.
- **A skipped case is not an executed case either.** A mapped class whose every case was skipped — an
  assumption aborted, a filter matched — also produced `"0 passing, 0 failing"` and `SUPPORTS`. It now
  takes the same `INCONCLUSIVE` path: `SKIPPED` is an outcome the runner reported, not an observation of
  the requirement.
- **The evidence line now states the executed count**: *"Existing tests mapped to X: 2 classes, 5
  executed, 5 passing, 0 failing"*. `0 passing` could previously mean "the cases ran and something
  odd happened" or "nothing ran"; the reader now sees which.
- **How it was found matters.** Running the tool on this repository did it: the self-check's exit-code
  requirement declares `tests: dev.codewitness.cli.EndToEndVerificationTest`, an `@Tag("e2e")` class the
  default suite excludes, so the class contributed no case at all — and the report still said
  *"Existing tests mapped to CWR-007: 1 classes, 0 passing, 0 failing"* with status `SUPPORTS`. That is
  the promotion of "we could not check" into "it passed" that the project forbids, and the run had no
  finding pointing at it because an evidence record is not a finding.

The rule was already implemented — for a different strategy. `GeneratedTestsStrategy` learned in an
earlier release that "no failing case was reported" is evidence of support only if a case was reported
at all; a generated test the runner never reported was scored as discharged. `ExistingTestsStrategy` is
its counterpart for the project's own suite and lacked the same guard. The two are now pinned by tests
of the same shape.

## What this does not fix

- **The same self-check run still carries a second, contradictory statement.** For the exit-code
  requirement, the unknown-aspects list says *"No executable scenario is declared for CWR-007, so
  CodeWitness could not run any experiment against it"* while the process scenario `SC-CWR-007` ran and
  discharged its obligation to `VERIFIED`. That is a separate defect, recorded in `docs/backlog.md`;
  it is not a consequence of this change, and suppressing or rewording the note is not the same fix as
  establishing whether a scenario exists.
- A requirement whose mapped test class exists but is *empty* (a class with no test methods) is also
  `INCONCLUSIVE` now — deliberately. The tool cannot tell "a placeholder class" from "a class the
  runner dropped", and neither is a passing test.

## Verified for this release

- Full reactor suite: **1757 tests, 0 failures** across all 22 modules (up from 1755: two regression
  tests).
- **The guard was proved to fire.** Both new tests fail against the unfixed strategy with
  `expected: <INCONCLUSIVE> but was: <SUPPORTS>`, reproducing the record the self-check produced, and
  pass after the change.
- Self-check (`./codewitness verify . --requirements selfcheck/requirements.yaml --config
  selfcheck/codewitness.yaml --no-mutation --max-duration 30m`): all seven ground rules `VERIFIED`, 0
  unsuppressed findings, exit `0`. The exit-code requirement's test evidence now reads *"Existing tests
  mapped to CWR-007: 1 classes, 0 executed, 0 passing, 0 failing"* with status `INCONCLUSIVE`, and the
  obligation is still `VERIFIED` — by the executed process scenario (`EV-021`), which is what actually
  ran. The verdict is unchanged and now consistent with its evidence.

## Compatibility

- No interface change. The CLI, the exit codes, the report keys, SARIF and every `codewitness.yaml` key
  are untouched. What changes is the *content* of one evidence record in a case that previously
  overstated it: `SUPPORTS` becomes `INCONCLUSIVE` when no mapped case executed, and its description
  gains the executed count. Verdicts move only where a requirement had no other evidence — and there
  they move from a silent partial support to an explicit `UNVERIFIED`, which is the direction this tool
  is built to fail in.
